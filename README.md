# tinymd

一个安静的 Markdown 工作空间。基于 **Electron 44** + **Tiptap 3**（含官方 `@tiptap/markdown`）构建，遵循苹果设计语言：大量留白、细腻的字排、克制的色彩。

![技术栈](assets/image20260924201526303.svg) ![tiptap](assets/image20260924201526349.svg)

## 功能

- **两种打开方式**：启动即欢迎页，可「打开文件夹」进入工作空间，也可直接打开单个 Markdown 文件（单文件模式：侧栏整个收起，只剩正文和右侧的目录，形态和独立窗口一样）；两者都进「最近打开」列表（最多记 5 条、默认露 2 条，其余在列表内滚动，不会把上方内容顶出窗口）。
- **文档目录树**：左侧递归展示当前文件夹内的文件夹与 Markdown 文件，自动监听磁盘变化并刷新。
- **独立窗口**：文件树右键某一篇 Markdown 选「在新窗口中打开」，会为它单开一个只显示正文的窗口 —— 没有文件树、没有底部的新建按钮，顶栏的「切换边栏」一并收起。与主窗口互不干扰：不切换主窗口正在编辑的文档，关掉它也不影响主窗口；主题是应用级设置，两个窗口会同步。用的是同一套页面与样式（`?mode=standalone`），排版完全一致。
- **一个文件只有一个窗口**：同一个 Markdown 不会同时开在两个窗口里 —— 两个窗口各存一份内存副本、各自自动保存，写回去就互相覆盖，而且界面上看不出来。已经打开过的文件再点「在新窗口中打开」不会再开一个，而是把已有的那个窗口切到前面（右键菜单里这一项会显示成「前往已打开的窗口」；就是当前这篇则灰显并标注「已在此窗口」）。在文件树里点到它、或从最近打开 / 拖拽 / 双击 / 命令行进来也是同一套判定：不切换当前文档、不换模式，只在状态栏说明一声。**不是**锁文件 —— 改完关掉窗口，或关掉工作空间，其它窗口就能接手。
- **文档目录（右侧固定区域）**：文档标题只在这一处看，主窗口、单文件模式、独立窗口都一样 —— 侧栏只放文件树。
  - **开关就在顶栏上**：与「纯文本模式 / 设置」同一排，是这一组最左边那个图标，一直显示在那里。左右留白固定 **20px**、两边一样宽（不再有窄 / 中 / 宽三档）。它原先住在正文右侧那条留白里、位置得从留白宽度反推，留白也就被迫「正好容纳一个图标」（58 = 14 + 30 + 14）；搬进顶栏之后这个约束没了，留白先收到 40、再按「尽可能窄又不影响美观」收到 **20**。⚠️ 20 是实测出来的下界：右边最外 10px 是滚动条槽，留白低于 20 时正文离滚动条不足 10px，末行的 `==高亮==`、行内代码底色就快贴上去了（16px 实测已经明显发紧）。左右留白也对齐过：滚动条会占掉右边一条，正文右侧内边距里把它扣掉，屏幕上的左右留白才真的一样宽。
  - **点一下显示、再点一下关闭**：`Ctrl/Cmd + Shift + O` 同效，`Esc` 也能收起。没有鼠标悬浮唤出，也没有「钉住」这回事 —— 只有开 / 关两种状态。
  - **区域尺寸是固定的**：宽 232px、上下都钉住（从顶栏下沿一直撑到状态栏上沿），**不随有没有标题、有几条标题变化**，所以展开 / 收起时不会忽高忽低；条目多时是自己内部滚动。
  - **往编辑区里摊开，窗口一动不动**：目录不是弹窗、不遮字，也不是把窗口撑宽，而是从右边**摊进编辑区** —— 展开时正文让出 246px（目录 232 + 留白 14）。左侧栏同理，收放时窗口尺寸一个像素都不变。窗口窄到 800 以下时两块怎么让路见下面那条。
  - **窗口窄到 800px 以下时，左右两块只能开一块**：点目录就把文件栏收起来，点文件栏就把目录收起来 —— 以你刚点的那块为准，并在状态栏说明一句。窗口被拖窄到 800 以下时也会自动收起目录。**800 及以上两块可以同时摊开**（哪怕正文被挤到两百多像素，那是你自己的选择，不拦）。窗口最小宽度 600。
  - **编辑区保底宽度 480px 只约束侧栏**：两块同开时侧栏不能宽到把正文挤到 480 以下 —— 拖拽上限、以及空间不够时把侧栏夹窄，都用这条线（窗口 800 且目录开着时侧栏会落到 180，正文还剩 364）。夹窄只是**这一次渲染出来的宽度**上的让位，你拖出来的宽度记着，空间回来会自动还给你（不会被永久改成那个窄值）。
  - **按钮不再跟着正文挪**：它在顶栏上，目录开与不开都在同一个位置，不需要去追。（早先它在右边留白里，展开目录时还得同步让位 246px 才能继续居中。）
  - 目录面板贴右缘留了 14px，不挡滚动条。点某一项跳转后目录留着，方便连着跳好几节。文档没有标题时不展开（点按钮只给一句状态栏提示）；纯文本模式下按钮置灰、目录自动收起。
- **可拖拽边栏**：侧栏右缘可拖动调整宽度（180–520px）并自动记忆。窗口不动，拖动直接改变编辑区宽度 —— 上限跟着窗口宽度与目录开合走，永远停在「正文还剩 480px」那条线上，不会把正文挤没；窗口被拖窄、或目录展开导致空间不够时也会被夹回来，但夹的只是**这一次渲染出来的宽度**，你拖出来的偏好值不受影响，空间回来就还给你。
- **主题切换**：在设置中心选择「暗色（中性）」或「亮色」并自动记忆，默认使用中性主题。设置是应用级的，多窗口同时打开时会即时同步。
- **所见即所得编辑**：Tiptap v3，支持标题、列表、任务列表、引用、代码块（含语言）、表格、图片、链接、高亮；输入 `# `、`- `、`> ` 等 Markdown 前缀自动转换格式，输入 `==文字==` 自动转为高亮。
- **纯文本模式**：可在顶栏切换到 Markdown 源文本编辑；切回所见即所得模式时，以当前纯文本重新加载整篇文档，避免两种视图状态不一致。
- **斜杠命令菜单**：在空行或词首输入 `/` 呼出插入菜单，支持标题、列表、任务、引用、代码块、表格、分割线、图片；继续输入可按名称 / 拼音缩写过滤（如 `/bg` → 表格），`↑↓` 选择、`Enter` 确认、`Esc` 关闭。代码块内不触发。
- **Markdown 双向转换**：使用官方 `@tiptap/markdown`（marked 内核）解析与序列化，保存时最大限度保留源文件语法（如 ```` ```js ```` 语言标记、`==高亮==`）。
- **自动保存**：停止输入约 0.6s 后自动写盘，`Ctrl/Cmd+S` 可立即保存；窗口关闭前兜底同步保存。
- **导出 PDF**：`文件 → 导出为 PDF…`（`Ctrl/Cmd+P`），或在文件树里直接右键某个 Markdown 选「导出为 PDF…」——后者导出的是被右键的那一篇，不一定是当前打开的。A4 纸张、带页脚页码，固定浅色输出（深色底印在纸上费墨且难读）。排版直接复用编辑器样式，长代码自动折行、不裁切，图片与中文都能正常输出。**两种编辑模式都支持**（纯文本模式导出的是文本框里的内容，未保存的改动也算），**导出不写盘、不切换当前文档**，被导出的那一篇一律在后台用同一套排版规则渲染。
- **导出 Word（.docx）**：`文件 → 导出为 Word…`（`Ctrl/Cmd+Shift+P`），或文件树右键选「导出为 Word…」。和导出 PDF 一样不分编辑模式、不写盘、不切换当前文档。产物是**真 .docx**：标题是 Word 的 Heading 样式（导航窗格 / 自动目录能认）、列表是 Word 的编号、表格与图片都是原生对象，可以在 Word 里继续编辑。代价见「关于 Word 导出的排版」一节。
- **图片原样本地存储**：粘贴 / 拖入 / 按钮插入图片时，原始二进制直接写入本地；Markdown 或富文本中的网络图片也会自动下载并替换为本地相对路径，不转 base64。可在图片设置中选择存储目录并调整网络图片大小上限（默认 30 MB）。
- **拖拽 / 右键打开 md**：把 `.md` 拖到窗口任意位置即可打开（欢迎页整页都是拖放区，仅顶部 38px 留给拖窗）；在资源管理器中右键 / 双击 Markdown 用「tinymd」打开，会以单文件模式载入该文件（开发模式可传参模拟，打包版依赖 `fileAssociations` 注册）。

## 开发

```bash
npm install        # 安装依赖（若 electron 二进制未下载：cd node_modules/electron && node install.js）
npm run dev        # Vite 开发服务器 + Electron（带 HMR）
```

## 打包

```bash
npm run dist:win   # Windows NSIS 安装包（x64）
npm run dist:mac   # macOS dmg（需在 macOS 上执行）
npm run dist       # 按 electron-builder.yml 默认平台打包
```

产物输出到 `release/`：`tinymd-<版本>-setup.exe`（NSIS 安装包）、`tinymd-<版本>-<架构>.dmg`（macOS 磁盘映像），以及 `win-unpacked/` 免安装版。

已配置 `.md` / `.markdown` 的 `fileAssociations`，打包安装后可在资源管理器双击 / 右键用「tinymd」打开。

> 上面三条命令已内置国内镜像（`ELECTRON_MIRROR` / `ELECTRON_BUILDER_BINARIES_MIRROR`）。
> 镜像刻意写在 npm 脚本而不是 `electron-builder.yml` 里：`@electron/get` 读取镜像的顺序是「环境变量 > 配置文件」，写进配置文件会连 CI 也一起走国内源，而 GitHub 的 runner 在海外。

## 发布

推一个 tag 就会自动出 Windows + macOS 安装包并创建 Release：

```bash
# 1. 改版本号：package.json 与 package-lock.json 里的根级和 packages[""]，共 3 处
#    （只改 package.json 会让 CI 的 npm ci 报版本不一致）
# 2. 提交后打 tag 并推送
git tag v0.2.1 && git push github v0.2.1
```

> 只想验证打包改动、不想发 Release？推一个**名字里带 `-` 的预发布 tag**（如 `v0.2.2-rc.1`），
> 按工作流里的条件它只构建、不发布。

产出的 Release 附件：

| 平台 | 附件 |
| --- | --- |
| Windows | `tinymd-<版本>-setup.exe`（NSIS 安装包）、`tinymd-<版本>-win-unpacked-x64.zip`（免安装版）、`latest.yml` |
| macOS | `tinymd-<版本>-universal.dmg`（一个 dmg 同时含 arm64 与 x64） |

工作流（`.github/workflows/release.yml`）分三个 job：`windows-latest` 与 `macos-latest` 各自打包并上传 artifact，最后一个 `publish` job 汇总两边的产物、用 `gh release` 统一创建 Release（不并发生成，也不会被两个平台互相覆盖）。macOS 那个 job 在打包后会跑一次签名自检（`codesign --verify --deep --strict`），确保 ad-hoc 签名确实生效且结构完好。

需要重跑时，在 Actions 页面对该 run 点 **Re-run all jobs**；用 **Run workflow** 手动触发时，选 tag 会发布、选分支只构建（发布步骤带 `--verify-tag`，tag 不存在会直接报错而不是静默发错版本）。

> 构建步骤里 `--publish never` 不能省。electron-builder 在 CI 环境下检测到 tag 会把发布模式隐式切成 `onTag`，再依据 `package.json` 的 `repository` 字段推断出 GitHub provider，接着因为拿不到 `GH_TOKEN` / `GITHUB_TOKEN` 而报错 —— 表面现象是「打包步骤莫名其妙失败」。发布统一交给 `gh release`，所以显式关掉它的自动发布。

### 前置检查

- 仓库 **Settings → Actions → General → Workflow permissions** 需要是 **Read and write permissions**，否则 `gh release` 会因 `GITHUB_TOKEN` 只读而 403（工作流里已声明 `permissions: contents: write`，但仓库设置为只读时无法提权）。
- CI 里不跑 `npm run build:icon`：`build/icon.png`、`build/icon.ico` 已提交入库，且与 `icon-candidate-25.*` 内容一致，直接在打包时复用。改图标后记得本地重跑 `npm run build:icon 25` 再提交。

## macOS 用户必读：首次打开会被拦截

**macOS 包带 ad-hoc 签名，但没有 Apple 开发者证书、未公证**。仓库里没有证书，CI 通过
`mac.identity: "-"` 显式启用 ad-hoc 签名（不写这行的话 electron-builder 找不到证书会直接跳过签名，
产物反而更差 —— 详见下面「想彻底去掉这个提示」）。

ad-hoc 签名是本地生成的、不需要任何账号的签名，作用有两个：让 App 的签名结构合法
（Apple Silicon 上未签名的二进制根本不允许运行），以及证明包在签完之后没被改动过。
但它**不包含开发者身份**，所以 Gatekeeper 依然会拦下它：

> 未打开「tinymd」 — Apple 无法验证「tinymd」是否包含可能危害 Mac 安全或泄漏隐私的恶意软件。

（不同 macOS 版本的文案略有差异，也可能显示为「已损坏」——那只是 Gatekeeper 的措辞，
不是文件真的坏了。）

**这是预期行为，不是包损坏。** 两种放行方式，任选其一：

### 方式 A：系统设置（Apple 官方途径，推荐）

1. 从这个对话框点 **「完成」** —— 不要点「移到废纸篓」。
2. 打开 **系统设置 → 隐私与安全性**，向下滚动到「**安全性**」区域。
3. 会看到一条「已阻止使用「tinymd」，因为来自身份不明的开发者」，点它旁边的 **「仍要打开」**。
4. 弹窗里再点一次 **「打开」**，然后输入密码 / Touch ID 确认。

批准一次即可，之后双击就能正常打开（系统会把它记为例外）。

> **找不到「仍要打开」按钮？** 该按钮**只在被拦下后的约一小时内出现**，且界面上没有任何倒计时提示
> （[Apple 官方说明](https://support.apple.com/zh-cn/guide/mac-help/mh40616/mac)：「此按钮在你尝试打开该 App 后一小时内可用」）。
> 按钮消失了就再双击一次 App 让它被拦下，然后立刻回到「隐私与安全性」。
> 另外先确认「允许从以下位置下载的 App」不是 **App Store**（选「App Store 和被认可的开发者」）。

更新到新版本后，新下载的 App 会被重新打上隔离标记，可能还需要再放行一次。

### 方式 B：终端清掉隔离标记（更快）

先把 App 从 dmg 拖进「应用程序」，然后执行：

```bash
xattr -cr /Applications/tinymd.app
```

### 两个常见误区

- ⚠️ **不要再按老教程「右键 → 打开」**。Apple 已在 macOS 15 (Sequoia) 起**移除**了 Control-click 覆盖 Gatekeeper 的能力
  （[Apple 官方说明](https://developer.apple.com/news/?id=saqachfa)），只能用方式 A 或 B。
- `sudo spctl --master-disable` 那套「允许任何来源」的老办法，在新版 macOS 上已被新的 Gatekeeper 工具堵掉，同样不可用。

### 关于签名的三个档位

| 签名方式 | 费用 | 用户看到什么 |
|---|---|---|
| 不做签名（找不到证书时 electron-builder 的默认行为） | — | 最差：签名结构缺失，对话框可能只剩「移到废纸篓」 |
| **ad-hoc 签名**（当前采用） | **免费** | 仍被拦一次，按上面方式 A / B 放行 |
| Developer ID 签名 + Apple 公证 | **$99/年** | 双击直接打开，零警告 |

只有第三档能真正消掉提示：需要 Apple Developer Program 账号（个人也能注册，但证书上会挂真实姓名），
用 Developer ID 证书签名后提交 Apple 公证（notarize）。这是独立的一套流程，目前未配置。

顺带一提，免费签名的替代渠道基本都已关闭 —— OSSign 的申请通道处于暂停状态，
Homebrew 自 2026-09 起也不再上架未通过 Gatekeeper 检查的软件。

## 设计说明

- 系统字体栈（SF Pro / 苹方 / 雅黑），自动跟随系统深浅色。
- Windows 使用 `titleBarOverlay`、macOS 使用 `hiddenInset`，自绘极简顶栏（可拖拽）。
- 图片经自定义 `app-file://` 协议读取，仅允许访问已打开的工作空间目录，以及单文件模式下文件所在的那个目录。
- 单文件模式不把所在文件夹当工作空间：主进程只为当前打开的那一个 Markdown（及其同目录下的其它 `.md`，用于相对链接跳转）开放读写，其它路径一律拒绝。
- 同一个 Markdown 同一时刻只允许在一个窗口里打开（主进程里一张「文档归属表」，`doc:claim` / `doc:release` / `doc:owner` 三个通道）：被占着时打开请求不会成功，只把持有它的窗口切到前面。归属随窗口走 —— 窗口切换文档就把上一篇让出去，窗口关闭、关闭工作空间、文档被删除时自动释放，所以关掉窗口后别的窗口立刻能接手（不是文件锁，进程退出后不留痕）。
- 文档目录区是一个挂在 `#content` 上的 `position: absolute` 区域，尺寸写死为「宽 232px + `top: 10px; bottom: 37px`」，条目数完全不参与高度计算；`body.toc-open` 时淡入展开（收起态是 `visibility: hidden` + `opacity: 0`，**不是 `display: none`** —— display 没法做过渡，而展开时正文要让位，只让正文动、面板啪一下冒出来会显得两件事没商量好；`visibility` 是离散量，转成可见时在 0% 就切过来、转成隐藏时留到最后，正好配合 `opacity`）。**没有鼠标热区，也没有 peek / pinned 两种态** —— 只有一个布尔量（`tocOpen`）和一条 `toggleToc()`，按钮和 `Ctrl/Cmd + Shift + O` 走的是同一条路。
- **「文档目录」按钮长在标题栏的 `.topbar-right` 里**（与「纯文本模式 / 设置」同排，是这一组最左边那个）：尺寸、圆角、悬停、按下态全部沿用 `.icon-btn`，位置交给 `flex + gap` 排 —— CSS 里没有一条 `#btn-toc` 的定位规则。⚠️ 它曾经是 `position: absolute` 挂在 `#content` 上、落在正文右侧那条留白里的，横向位置由 `--toc-btn-right = calc((--content-pad - --toc-btn-w) / 2)` 从留白宽度反推，展开目录时还要 `right: +246px` 跟着正文一起走（早先窗口会跟着变宽时，那个 246 的作用是「让按钮在屏幕上原地不动」—— 数值一样、语义相反）。搬进标题栏之后那套算式连同 `--toc-btn-w` / `--toc-btn-right` 一起删了，别再复活。ID 仍是 `#btn-toc`，JS 那边（可用性、`active` 态、点击 / 快捷键）一行没动。
- **⚠️ `var()` 在自定义属性里的代入时机**：`--x: calc(var(--content-pad) / 2)` 若写在 `:root` 里，代入的是 **`:root` 自己的** `--content-pad`，而 `--content-pad` 一旦被挪到 `body` 上按档位覆盖（早先的窄 / 中 / 宽三档就是这么干的），这里代进去的还是 `:root` 的那个值 —— 三档按钮会齐齐停在同一个位置（实测踩过，还是靠**三档各量一次**才发现的）。结论：这类「由别的变量推出来的变量」必须和它依赖的变量**声明在同一个元素**上，或者干脆把 `calc()` 写在使用处。现在留白固定了、不存在分档覆盖，但这条约束仍然写在这里，因为它是加档位时最容易踩的坑（当年的实例就是 `--toc-btn-right`，已随按钮搬进标题栏一起删掉）。
- **左右留白一样宽**：正文左右内边距本来都是 `--content-pad`，但 `#editor-wrap` 的滚动条竖在窗口右缘、等于在右边再多占一条（Windows 10px、macOS 的 overlay 滚动条 0），肉眼看就是「右边更宽」。渲染层启动时用**离屏探针**实测一次滚动条宽度写进 `--sb-w`，正文右侧内边距改成 `calc(var(--content-pad) - var(--sb-w))`，左右留白才对等（纯文本模式的 `#source-editor` 同一套算法）。⚠️ 这个「对等」是**视觉**上的：正文排版边界到面板边界的距离两边都是 `--content-pad`，所以最窄处（正文 → 滚动条左缘）只有 `--content-pad - --sb-w`。正因为这条，`--content-pad` 有个下界 —— 20px 时最窄处剩 10px，还是分得开的；再往下调就贴上了。这个实测值同时被 JS 记了一份（`scrollbarWidth`），给「编辑区保底宽度」算账时要扣掉它 —— 底线说的是正文真正能用到的宽度，不扣的话屏幕上会莫名其妙地少 10px。⚠️ 探针不能直接量 `#editor-wrap` —— 没打开文件时它是 `display: none`，`offsetWidth` 和 `clientWidth` 都是 0，量出来永远是 0。`scrollbar-gutter: stable` 让槽位常驻，正文从「不满一屏」长到「溢出一行」时不会横向抖一下。⚠️ `--sb-w` 的默认值是 0px，正是给导出 PDF 的隐藏窗口用的（那边没有滚动条，左右内边距照样相等）。⚠️ **PDF / Word 导出不吃这个值**：导出页只注入一个裸的 `<div class="ProseMirror">`（没有 `#editor` 外壳），纸面边距由 `printToPDF` 的 `margins` 和 docx 的 `PAGE_MARGIN` 各自决定 —— 所以改 `--content-pad` 不会把 PDF 边距一起改窄。
- **两侧面板都往编辑区里摊，窗口一动不动**：侧栏的布局宽度（264 → 0）和目录的让位（`body.toc-open` 给编辑区加 `margin-right: 246px`）都是页内重排。`ui:resize` 只管欢迎页 480 / 工作区 1000 这两套基准尺寸，与面板无关 —— 所以「主进程按增量挪窗口」那套机械（`window:pad` / `applyWindowPanels` / 最大化后补账）已经整段删掉了，单文件模式的窗口也不再比工作区窄一条（那 264px 直接还给编辑区）。
  - **工作区宽度为什么是 1000**：它是「侧栏 264 + 编辑区 + 目录 246」一起住的那个宽度，按用户要求收窄到 1000（历史：1020 → 1180 → 1200 → 1000）。1000 时两块面板同开，正文可用 = `1000 − 264 − 246 − 滚动条 10` = **480**，正好压在 `EDITOR_MIN` 上 —— 侧栏一分都不用让。**这个数不再有下限**：面板能不能同开已由 `PANELS_EXCLUSIVE_W`(800) 单独决定，跟基准宽度无关（早先「不能小于 990」那条约束随之作废）。
  - **窗口最小宽度分两套**：工作区 `600`、欢迎页 `460`（欢迎页本身只有 480 宽，拿 600 卡它连创建都别扭）。`ui:resize` 里**先松最小宽度、再换尺寸** —— 顺序反了的话，从工作区退回欢迎页会被 600 卡住、缩不到 480。
  - **换尺寸后夹回工作区**：两套基准尺寸差 700px 宽，贴右站着的窗口（或在分屏 / 小屏上）一切到工作区就会有一条跑到屏幕外，所以 `ui:resize` 走 `fitToWorkArea()` —— **只挪位置，不改尺寸**；窗口本身比工作区还大的时候贴左上，不去缩它。
  - **为什么不再改窗口尺寸**：窗口几何只能**瞬时**变（`setBounds` 没有动画可放），而侧栏宽度是带动画的 —— 一改窗口两者必然错帧：收起时窗口先跳到窄尺寸、侧栏还要 180ms 才缩完，正文被挤窄再弹回；展开时窗口先长出去、侧栏才慢慢长出来，正文先撑宽再收回来（用户原话：「先把编辑区拓展过去，把文件区显示出来，把编辑区缩回去」）。要真正对齐只能 rAF 逐帧同时改侧栏宽和 `setBounds`，但两边的时间线由不同进程驱动、必然差一两帧，那点残差会变成正文的横向抖动。窗口不动就完全没有这一类问题，动画反而能放回来：`#sidebar { transition: width }`、编辑区 `transition: margin-right`、目录面板 `opacity` + `transform` 淡入（只有拖拽调宽时才用 `body.resizing` 关掉侧栏的过渡）。
  - **互斥与否只看窗口宽度：`PANELS_EXCLUSIVE_W = 800`**（渲染层常量）。窄于它时左右两块只能开一块，三条路共用这一条判据：开目录（`setTocOpen`）、开侧栏（`toggleSidebar`）、窗口被拖窄（`resize` 监听）—— 都以「刚点的那块为准」把另一块收掉，并 `setStatus` 说明一句（面板自己消失最容易让人以为点坏了）。**800 及以上允许同开**，正文被挤窄不拦。⚠️ `resize` 那条要判 `hasSidebar()`：单文件模式、或侧栏本来就收着时，目录没跟谁抢位置，不该被收掉。
  - **`EDITOR_MIN = 480` 如今只干一件事：给侧栏宽度定上限**（`sidebarMaxWidth`，拖拽与夹窄共用；口径是「正文能用到的宽度」，所以算账要扣掉滚动条）。800–1000 这一区间两块同开时侧栏会被夹窄（800 宽下夹到 180、正文剩 364），这是必要的降级。
  - **侧栏宽度只有一个出口 `applySidebarWidth()`**：渲染宽度 = 偏好宽度（`sidebarPref`）∩ 此刻上限，收着的时候也照算。⚠️ 夹窄**不写 localStorage** —— 早先的写法把夹取值写回 DOM 并持久化，于是在窄窗口里开一次目录侧栏就被永久记住那个窄值（900 宽下夹到 180，窗口拉回来还是 180）；现在空间一回来就自动还给你，节点上那句「偏好的归偏好、渲染的归渲染」也是同一条。
  - 验证方式：逐帧采 `#editor-wrap.clientWidth`，断言「开合期间窗口宽度全程不变」+「编辑区宽度单调、不越出首末两帧」—— 旧的窗口方案在这两条上必挂。
- 删除操作移入系统废纸篓（可恢复），不做不可逆删除。

## 关于 Word 导出的排版

导出 PDF 之所以能和编辑器像素一致，是因为把 `style.css` 原样重放进隐藏窗口再打印。
**Word 不吃 CSS，这条路不存在** —— docx 的样式是在 `docx-export.cjs` 里照着
`style.css` 的数值**手抄一份**成 Word 自己的排版元素（标题样式、编号列表、表格底纹）。

由此有三个要知道的后果：

- **排版是近似的，不会与编辑器完全一致**。字号、行距、段间距、颜色都已经对到同一组数值，
  但字体由 Word 按系统替换，分页也由 Word 自己算。
- **改 `style.css` 不会自动同步到 docx**。这是与 PDF 最大的维护差异，改版式时两边都要看。
- **少数内容会被简化**：任务列表用 `☐` / `☑` 字面前缀（Word 没有「仅作标记」的复选框编号）；
  代码块的语言角标不导出（它和 PDF 那边一样属于编辑器 UI，不是文档内容）；
  `webp` / `avif` 图片无法嵌入（`docx` 库的 `ImageRun` 只认 png / jpeg / gif / bmp / svg），
  这类图片会被跳过，并在状态栏告知张数，不会静默丢失。
